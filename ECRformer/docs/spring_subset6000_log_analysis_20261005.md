# Spring 6,000개 학습 로그 분석 및 개선 계획

분석일: 2026-10-05. 실행 기록의 시간대는 한국 표준시(KST)입니다.

## 결론

학습 프로세스는 정상 종료했지만, epoch 16부터 학습·검증 오차가 동시에 급증했습니다. epoch 8의 체크포인트를 평가 기준으로 보존하고, 마지막 체크포인트에서 그대로 학습을 재개하지 않는 것을 권합니다. 모델 구조 변경이나 데이터 확대보다 발산 원인 분리와 안정성 확인이 우선입니다.

이 문서는 서버에서 읽은 로그·설정·코드를 바탕으로 작성했습니다. 원본 로그, TIFF, 체크포인트는 이 문서 커밋에 포함하지 않습니다. 개선 실험과 코드 수정, 재학습은 아직 수행하지 않았습니다. 아래 지표는 **검증 세트 지표이며 별도 테스트 성능이 아닙니다.**

## 실행 조건과 종료 상태

| 항목 | 확인한 값 |
| --- | --- |
| 실험 | `ecrformer_spring_spring_subset6000/version_0` |
| 장비 | Windows, RTX 3060 Ti 8GB, RAM 16GB |
| 모델 | ECRformer 전체 모델, 약 11.37M 파라미터(light 모델 아님) |
| 데이터 | spring train 24,378개 중 고정 6,000개, validation 756개 |
| seed / crop | 42 / 128 × 128 |
| 정밀도 / 배치 | `16-mixed` / train 2, validation 1 |
| accumulation / 유효 배치 | 8 / 단일 GPU에서 16 |
| optimizer / 학습률 | AdamW / 0.0004 |
| 최대 epoch / 조기 종료 patience | 200 / 10 |
| gradient clipping | 0.5 (이미 적용됨) |
| 최신 재개 실행 | 2026-10-04 14:48:08 시작 → 18:12:03 종료 |
| 종료 | `exit_code=0`, 검증 손실 10회 연속 미개선으로 조기 종료 |

최신 실행은 기존 `last.ckpt`에서 전체 학습 상태를 복원한 재개 실행입니다. 새로 처음부터 시작한 실험이 아닙니다. 로그 epoch는 0부터 시작하며 마지막 완료 epoch는 18(전체 학습 이력상 19번째 epoch), global step은 7,125입니다. 이번 실제 실행은 앞서 문서에 안내한 1,000개/100 epoch 예시와 구분해야 합니다.

epoch당 train 3,000배치, optimizer 업데이트 375회이며 최근 epoch는 검증 포함 약 16분 52초~16분 58초였습니다. 최대 CUDA 할당 메모리는 약 4,130MiB, 예약 메모리는 4,260MiB였습니다. GPU 메모리 부족 예외는 확인되지 않았습니다.

## 성능 변화와 최초 이상 구간

| epoch(0부터) | 학습 MAE 평균 ↓ | 검증 MAE ↓ | 검증 PSNR(dB) ↑ | 검증 SSIM ↑ | 검증 loss ↓ |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 (최적) | 0.040728 | 0.022640 | 30.030531 | 0.912831 | 0.029093 |
| 15 | 0.039295 | 0.031105 | 28.259220 | 0.870403 | 0.040954 |
| 16 | 7.999050 | 21.068518 | -26.853853 | -0.000260 | 19.061686 |
| 17 | 15.830757 | 27.591515 | -29.107327 | 0.000063 | 24.932331 |
| 18 | 57.833340 | 64.329369 | -36.421108 | 0.000013 | 57.996456 |

epoch 16의 `TRAIN_PROGRESS` 기록에서 누적 학습 MAE는 배치 200에 0.039420, 400에 0.080967, 600에 0.636774로 상승했습니다. **배치 201~400 구간에 이상 징후가 시작됐다고 좁힐 수 있지만 정확한 최초 배치·샘플은 확인할 수 없습니다.** 이 수치는 각 구간만의 평균이 아니라 epoch 시작부터의 누적 평균입니다.

학습 오차까지 함께 폭증했으므로 검증 성능만 떨어지는 일반적인 과적합보다 학습 발산 양상에 가깝습니다. 최종 검증 RMSE는 66.229988로, 정상 전처리 후 광학 정답 범위가 0~1인 설정에 비해 매우 큰 오차입니다. 지표 계산은 예측을 0~1로 잘라내지 않으므로 음수 PSNR 자체를 지표 계산 오류로 단정할 수 없습니다.

## 확인된 사실과 원인 후보

### 확인된 사실

- 종료를 직접 촉발한 것은 `valid_loss` 10회 연속 미개선입니다. 최신 stderr에 조기 종료 메시지가 있고 stdout에 정상 종료 코드가 있습니다.
- OOM이나 실행 예외는 최신 로그에서 확인되지 않았습니다. 경고 메시지만으로 학습 실패를 의미하지 않습니다.
- epoch 8과 18의 저장된 모델 가중치에서 NaN/Inf는 발견되지 않았습니다. 유한한 가중치만으로 중간 활성값·gradient·예측이 정상임을 보장하지는 않습니다.
- 학습률은 악화 이후에도 0.0004였습니다. 현재 MultiStepLR 감소 시점은 `[120, 150, 170, 180, 190, 200]`이므로 이번 종료 전에는 감소하지 않았습니다.
- 데이터 로더는 광학 0~10,000 및 SAR -25~0을 clip·정규화하고 NaN 처리를 수행합니다. 데이터 경로를 못 읽어 샘플 수가 0인 문제는 이번 로그와 다릅니다. 전체 데이터의 정합·품질까지 검증한 것은 아닙니다.

### 아직 확정되지 않은 원인 후보

- **학습률과 업데이트 안정성:** 현재 학습률이 이번 조건에서 과도했을 가능성은 있으나 낮은 학습률 비교가 없어 확정할 수 없습니다. 검증 정체에 대응하는 학습률 감소가 없었다는 사실과 최초 발산 원인은 구분해야 합니다.
- **FP16 및 SSIM 손실의 수치 안정성:** SSIM 코드에 `.float()` 변환이 있지만 autocast를 명시적으로 해제하는 구간은 없습니다. FP32 실행과 비교하지 않았으므로 FP16이 원인이라고 단정할 수 없습니다.
- **특정 샘플·보조 손실·중간 활성값 또는 gradient의 이상:** 현재 기록만으로 최초 이상 샘플이나 연산을 특정할 수 없습니다. 고정 목록이어도 순서와 랜덤 crop·증강은 바뀔 수 있습니다.

## 개선 및 검증 순서 (미실행 계획)

1. **현재 기준 성능 확보:** `epoch=8-step=3375.ckpt`를 별도 테스트 분할에서 평가하고, 구름 비율별 지표와 예측 이미지를 확인합니다. 검증 최고점이 테스트 성능을 보장하지는 않습니다.
2. **학습률 단독 비교:** 같은 데이터 목록·seed·배치·정밀도를 유지하고 0.0004와 0.0001을 비교합니다. 0.0001은 첫 비교 후보이지 입증된 최적값이 아닙니다. 동일 초기 상태의 별도 실험을 사용하고, 발산한 마지막 checkpoint의 optimizer 상태와 새 설정을 무심코 혼용하지 않습니다.
3. **정밀도 단독 비교:** 다른 조건을 유지한 FP32/FP16 비교로 정밀도 영향을 확인합니다. FP32에서 메모리가 부족하면 배치 조정은 별도 변경으로 기록해 비교의 한계를 명시합니다. 문제가 FP16에 국한되면 SSIM 등 민감한 손실 구간에서 autocast 해제와 FP32 입력 사용을 검토합니다.
4. **배치별 진단 보강:** 주 손실·down/up 보조 손실, 예측 최솟값/최댓값, gradient norm(clip 전후), 유한값 여부와 원본 샘플 경로를 기록합니다. 비정상 값 발생 시 중단·별도 기록하는 방안도 검토합니다. 기존 clipping 0.5가 있으므로 단순 추가를 해결책으로 제시하지 않습니다.
5. **학습률 스케줄 개선:** 검증 성능 정체 시 감소하는 ReduceLROnPlateau 등을 검토합니다. 예를 들어 감소 patience 3~5는 실험 후보이며, 감소 후 회복할 시간이 조기 종료 전에 확보되도록 조정합니다. 조기 종료 patience만 늘려 발산 상태를 오래 학습하는 것은 피합니다.
6. **안정화 후 데이터 확대:** 지역·구름 비율의 대표성, SAR/광학/정답 대응과 정합, train/validation/test 누수를 점검한 후 6,000개에서 전체 train으로 확대합니다. 모델 구조 확장이나 손실 가중치 변경은 안정적인 기준 실험이 확보된 이후 별도 비교합니다.

실험마다 별도 이름·로그 폴더를 사용하고 한 번에 하나의 요인을 바꿉니다. 비교에 사용하는 데이터 목록과 평가 분할을 고정하며, 여러 seed에서도 재현되는지 확인합니다. 짧은 실행 성공만으로 안정화됐다고 판단하지 말고 기존 발산 시점을 넘어 안정적으로 진행되는지와 최적 검증·테스트 성능을 함께 봅니다. 성능 개선은 아직 보장되거나 측정되지 않았습니다.

## 서버 로그 안내

기본 위치: `C:\CtrS\ECRformer\Official_ECRformer`.

| 이름 앞부분 (각각 `.stdout.log` / `.stderr.log`) | 의미 |
| --- | --- |
| `spring_train` | 전체 spring train 초기 실행. 기록은 epoch 0 도중 끝남 |
| `spring_subset_train` | 고정 6,000개 최초 실행. 기록은 epoch 7 도중 끝남 |
| `spring_subset_resume_20261004` | checkpoint 재개 실행. 기록은 epoch 7 초반까지 |
| `spring_subset_resume_detailed` | 최신 상세 재개 실행. epoch 18 이후 조기 종료 및 종료 코드 기록 |

앞의 세 로그가 도중에 끝난 정확한 이유는 이번 확인 범위에서 확정하지 않았습니다. `stdout`은 일반 출력·진행률, `stderr`는 경고·예외·라이브러리 안내·조기 종료 메시지입니다. stderr 파일 존재 자체는 오류의 증거가 아닙니다.

최신 실험 폴더: `experiments\ecrformer_spring_spring_subset6000\version_0`.

| 파일 | 용도 |
| --- | --- |
| `training_diagnostics.jsonl` | 배치 200개 간격의 누적 진행, epoch 요약, 검증 지표, 시간·학습률·GPU 메모리 등 분석용 상세 기록 |
| `events.out.tfevents...` 3개 | 최초 실행 및 두 재개 실행의 TensorBoard 그래프 기록 |
| `hparams.yaml` | 저장된 실험 설정. 재개 후 모든 변경 이력을 나타내지는 않으므로 실행 로그와 함께 확인 |
| `train_subset.json` | 고정 학습 샘플 목록. 성능 로그 아님 |
| `checkpoints\epoch=8-step=3375.ckpt` | 가장 낮은 검증 손실을 기록한 평가 후보 |
| `checkpoints\last.ckpt` | 성능이 무너진 epoch 18의 재개용 상태 |

서버 경로는 증거 위치 안내이며 GitHub에서 원본 파일을 열 수 있는 링크가 아닙니다. 원본 로그와 checkpoint는 서버에 유지합니다. 접근 암호나 인증 정보는 문서에 기록하지 않습니다.
